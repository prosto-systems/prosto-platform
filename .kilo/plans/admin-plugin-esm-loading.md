# Admin Plugin ESM Loading

## Goal

Load every admin plugin asset declared as `type: 'script'` as an ESM module instead of a classic JavaScript script, while preserving manifest order, cache busting, module metadata, and the current continue-on-error behavior.

## Decisions

- Use a dynamically appended `<script type="module">`; do not replace the loader with `import()`, because the existing DOM lifecycle, `data-module-id` marker, and `load`/`error` handling remain useful.
- Apply ESM semantics to both plugin entries and script-valued `contentFiles`, since both pass through the same `injectScript` API and the manifest contract does not distinguish classic scripts from modules.
- Do not add a classic-script fallback. The requested runtime format and the example plugin build are already ESM.
- Do not change `platform-sdk` or the Zod manifest schema: `type: 'script'` identifies the asset category, while the shell owns its browser loading semantics.

## Implementation

1. Update `packages/platform-admin-shell/src/features/platform/utils/plugins.utils.ts` so `injectScript` sets `HTMLScriptElement.type` to `module` before appending the element. Retain `async = false`, the hashed URL generated by `getUrlWithCache`, `data-module-id`, sequential Promise completion, and error logging/continuation.
2. Add `packages/platform-admin-shell/src/features/platform/utils/plugins.utils.test.ts` using Vitest and happy-dom. Invoke `injectScript`, inspect the appended element, and assert that it is a module script with the expected URL/cache hash and module ID; dispatch `load` and await the returned Promise so the asynchronous contract is covered. Clean up the inserted test element after each case.
3. Keep `examples/module-test/vite.config.ts` unchanged: its admin build already uses Vite library mode with `formats: ['es']` and therefore provides the expected module artifact.

## Failure Modes And Rollout

- Browser ESM loading requires JavaScript module-compatible MIME responses and, for cross-origin plugin URLs, valid CORS headers. A deployment that served classic bundles or relied on permissive classic-script cross-origin behavior will fail through the existing `script.onerror` path and log the plugin URL.
- No manifest migration is required. Deploy ESM plugin artifacts together with the shell change; the repository example already satisfies this requirement.
- Existing topological loading remains serial because `loadPlugins` waits for each `injectScript` Promise before appending the next script.

## Validation

1. Run `npm run test -- --filter=@prosto/platform-admin-shell`.
2. Run `npm run typecheck -- --filter=@prosto/platform-admin-shell`.
3. Run `npm run lint -- packages/platform-admin-shell/src/features/platform/utils/plugins.utils.ts packages/platform-admin-shell/src/features/platform/utils/plugins.utils.test.ts`.
4. Run `npm run build -- --filter=@examples/module-test --filter=@prosto/platform-admin-shell` to verify the ESM example artifact and shell build remain compatible.
